## 0. 通用约定

### 0.1 模板清单

| 编号 | 模板名 | 对应需求 | 落库位置 | 状态 |
| --- | --- | --- | --- | --- |
| T-01 | 岗位技能抽取 | REQ-17~19、AC-AI-01/05 | `ai_db.extraction_result`；标签经 `skill_tag`、`job_skill` 关联岗位 | 已实现 |
| T-02 | 企业行业识别 | REQ-45、AC-AI-06 | 接口返回，不落库 | 已实现 |
| T-03 | 导入字段映射 | REQ-46、AC-AI-07 | 预览接口返回，人工确认后才进入导入 | 已实现 |
| T-04 | 课程体系调整建议草稿 | REQ-47、AC-AI-08 | `curriculum_db.adjustment_plan_item` | 已实现 |

### 0.2 五段式结构

每个模板固定五段，顺序不可调换：

1. **角色**：一句话说明模型在这里做什么。
2. **输入 schema**：逐字段说明含义，明确「哪个字段是唯一依据」。
3. **任务规则**：可判定的规则，每条都能写成断言。
4. **输出硬性要求**：结构、类型、枚举值、禁止项。
5. **兜底**：判定不了时输出什么。没有兜底的模板一定会编。

### 0.3 三条全局硬约束

对四个模板全部生效：

1. **只从给定集合选，不得编造标识符。** 输入给了标准字段、课程技能点等候选集合时，输出必须来自该集合；给不出就输出「待确认」。
2. **不得输出系统态。** 模型只回答业务判断，不回答「服务是否可用」「解析是否失败」。这些是后端状态，模型只负责给业务结论。
3. **判定不了要给低置信度或待确认，不得给假结论。** 错误的自动结论比没有结论危害更大。

### 0.4 调用、切批与回退

- **切批：** 抽取按字符数切批，`len(岗位名称) + len(职位描述)` 累计超过 12000 字符或 50 条即切断；其余模板单次调用。
- **串行模板、并行批次：** 同一批数据不并发跑两个不同模板；不同批次可并发。
- **超时与重试：** 单次超时 60s；失败按 1m / 5m / 30m / 2h 退避，累计 5 次转人工。
- **回退：** 模型不可用、超时、返回非法 JSON、字段类型不符或 id 对不上时，按规则回退，并在响应中标注 `provider`、`model`、`fallback`、`note`。回退也失败才返回 502，不得返回空结果冒充成功。
- **日志：** 每次失败必须记录 `traceId`、业务批次号、业务主键、失败类型（`timeout` / `http_4xx` / `http_5xx` / `invalid_json` / `field_mismatch`）与原始响应前 500 字符。

### 0.5 版本与实现位置

- 每个模板有 `templateId@version`（本文为 `T-01@v1` ~ `T-04@v1`），调用日志记录实际版本。
- 本文档是提示词版本基线。当前实现中的提示词常量位于：
  - T-01：`backend/ai-service/.../llm/OpenAiCompatibleLlmClient.java`
  - T-02：`backend/ai-service/.../assist/CompanyClassifyService.java`
  - T-03：`backend/ai-service/.../assist/FieldMappingService.java`
  - T-04：`backend/ai-service/.../assist/AdjustmentSuggestionService.java`
- 代码常量为当前运行版本，本文档为规范版本；两者措辞不一致时以本文档为目标，并在下一次发版时同步升版，保留可追溯的版本号。

### 0.6 这件事不做什么

- **不做多轮对话。** 四个模板都是单轮：一进一出，无上下文。
- **不做长文生成。** 输出必须是可被 JSON 解析的结构；报告正文、课程大纲走模板渲染，不交给模型。
- **不做需要外部工具的动作。** 无联网检索、无数据库查询。
- **不替代人工确认。** 字段映射与调整建议都是「建议」，确认动作由人完成。

## 1. T-01 岗位技能抽取

**用途：** 从 `job_sample.description` 抽取技能、工具、工程能力三类标签，写入抽取结果并由数据服务关联 `skill_tag` / `job_skill`。
**定位：** 只产原文词，不做标准化；标准化不在本项目当前范围内。

### 1.1 输入

```json
{
  "jobId": 1001,
  "jobTitle": "Java开发工程师",
  "description": "岗位职责：负责微服务架构设计与核心模块开发；任职要求：熟悉Spring Boot、MyBatis，了解Docker与Kubernetes，有代码评审经验。"
}
```

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `jobId` | `job_sample.id` | 原样带回，后端据此回写 |
| `jobTitle` | `job_sample.job_title` | 仅作上下文，**不得据标题推断技能** |
| `description` | `job_sample.description` | **唯一抽取依据** |

### 1.2 提示词

```
你是招聘岗位的技能抽取助手。任务是从岗位描述原文里，把岗位明确要求的技术能力摘出来，按技能、工具、工程能力三类归档。

输入是一条岗位 JSON：
- jobId：岗位编号，原样带回；
- jobTitle：岗位名称，只作上下文参考，不要从标题推断技能；
- description：岗位描述原文，这是你唯一的抽取依据。

抽取规则：
1. 只抽 description 里实际出现过的词。原文写「熟悉 Spring Boot」就抽 Spring Boot；原文只写「熟悉主流开发框架」，就什么都不抽，不要猜是哪个框架。
2. 每个词归入且只归入一类：
   - 工具：可具名的产品或平台，如 Spring Boot、MySQL、Kubernetes、Cursor；
   - 技能：可迁移的方法或领域能力，如 微服务设计、性能调优、需求分析；
   - 工程能力：对工作方式的要求，如 代码评审、持续集成、技术文档写作。
   同一个词只能出现在一类里，不要重复。
3. 保留原文写法，不翻译、不改写成标准名、不合并同义词。原文写 SpringBoot2.x 就返回 SpringBoot2.x。
4. 学历、工作年限、薪资、年龄、性别、户籍、出差意愿这类要求，不属于技术能力，不要抽。
5. description 里确实没有任何技术词时，三类都返回空数组，不要硬凑。

输出要求：
- 只返回一个 JSON 对象，不要解释、不要 markdown 代码块、不要注释；
- 结构：{"skills":[],"tools":[],"abilities":[]}；
- 三个字段都必须是数组，元素为字符串，不允许 null；
- 数组内去重，保持原文出现顺序。
```

### 1.3 输出

```json
{
  "skills": ["微服务架构设计", "核心模块开发"],
  "tools": ["Spring Boot", "MyBatis", "Docker", "Kubernetes"],
  "abilities": ["代码评审"]
}
```

### 1.4 后端必须做的校验

| 校验 | 处理 |
| --- | --- |
| 三个字段任一为 null | 视为解析失败，按未抽取处理并进重试 |
| 数组元素为空串、纯数字、超 100 字 | 丢弃该标签，其余保留 |
| 同一标签同时出现在两类 | 按 工具 > 技能 > 工程能力 的优先级保留一个，并记日志 |
| 模型未返回 jobId | 单条抽取可忽略；批量抽取按未抽取处理 |
| 规则回退 | 使用 `skill-dictionary.json` 命中词生成三类结果，并标注 `provider=rule` |

### 1.5 已知限制

- 模型可能把「了解」和「精通」当成同一件事；本项目不区分熟练度，`spec.md` 未要求分级。
- 长描述（超 2000 字）召回会下降；如需提升，按段落二次切分后合并去重，不得改变「只抽原文」的口径。

## 2. T-02 企业行业识别

**用途：** 判断企业主营业务是否属于软件、数据服务、人工智能、云计算四类，为 AI 工作台展示与后续覆盖率统计提供依据。
**定位：** 只回答「企业属于哪一类」，不回答「目标企业清单里该不该有它」。

### 2.1 输入

```json
{
  "companies": [
    { "id": "1", "companyName": "南京云创大数据科技股份有限公司" },
    { "id": "2", "companyName": "江苏润和软件股份有限公司" },
    { "id": "3", "companyName": "南京老王餐饮管理有限公司" }
  ]
}
```

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `id` | 调用方生成 | 原样带回，不依赖数组顺序 |
| `companyName` | `company.company_name` | **唯一判定依据** |

### 2.2 提示词

```
你是企业赛道分类助手。任务是根据企业名称判断它的主营业务是否属于软件、数据服务、人工智能、云计算这四类。

输入是一个 JSON 对象，companies 里每项有 id（企业编码）与 companyName（企业名称）。

分类规则：
1. 只按主营业务判断，不按名称里是否含「科技」「智能」「网络」这类字眼判断。「智能」出现在一家做智能硬件的公司名里，不代表它属于人工智能赛道。
2. 四类只能选最贴近主营的一个：
   - 软件：企业软件、行业应用软件、SaaS、系统集成；
   - 数据：数据服务、数据治理、数据分析、数据标注；
   - 人工智能：算法与模型研发、AI 应用产品、计算机视觉、自然语言处理；
   - 云计算：云平台、云基础设施、云原生服务。
3. 判断不了就归为其他，不要为了给结论而强行归类，并把置信度调低。
4. 名称有明显歧义时按输入字面判断，不要假设是某个知名企业；集团与子公司按输入名称判断，不自动扩展到母公司。
5. 只有企业名称这一个依据，不得依据行业常识之外的猜测补全信息。

输出要求：
- 只返回一个 JSON 对象，不要解释、不要 markdown；
- 结构：{"items":[{"id":"1","companyName":"...","aiFlag":1,"confidence":0.86,"reason":"主营网络安全软件产品与服务"}]}
- aiFlag 为数字：属于上述四类为 1，其他为 0；
- confidence 是 0 到 1 之间的小数；
- 每个输入企业必须对应输出一条，id 与 companyName 原样带回。
```

### 2.3 输出

```json
{
  "items": [
    { "id": "1", "companyName": "南京云创大数据科技股份有限公司", "aiFlag": 1, "confidence": 0.88, "reason": "主营大数据与数据服务" },
    { "id": "2", "companyName": "江苏润和软件股份有限公司", "aiFlag": 1, "confidence": 0.92, "reason": "主营行业应用软件与软件服务" },
    { "id": "3", "companyName": "南京老王餐饮管理有限公司", "aiFlag": 0, "confidence": 0.9, "reason": "主营餐饮服务，不属于四类赛道" }
  ]
}
```

### 2.4 后端必须做的校验

| 校验 | 处理 |
| --- | --- |
| `aiFlag` 不是 0/1 | 该条按规则回退重算，并记日志 |
| 缺少某个输入企业 | 用规则补齐，不允许少返回 |
| `confidence < 0.60` | 保留结果但标注低置信度；当前接口不落库，不参与统计 |
| 模型不可用 / 非法 JSON | 按关键词规则回退，响应 `fallback=true` |
| 规则回退口径 | 名称含 软件/信息/数据/智能/人工智能/云/科技/网络/计算/大数据/算法/IT/数字/自动化/互联/电子 判 1，否则 0 |

### 2.5 已知限制

- 仅凭企业名称判断，同名、简称、集团子公司会误判；结果只用于辅助展示，不作为唯一事实。
- 当前不落库，不参与看板 AI 岗位占比；看板占比仍按岗位名称关键词统计（见 §5）。

## 3. T-03 导入字段映射

**用途：** 把外部 Excel/CSV 表头映射到系统导入模板标准字段，返回预览，供人工确认。
**定位：** 模型只给建议；预览接口不落库，不自动开始导入。

### 3.1 输入

```json
{
  "databaseFields": {
    "companyName": "公司名称",
    "jobTitle": "岗位",
    "workLocation": "工作地点",
    "description": "职位描述",
    "salary": "待遇",
    "experience": "经验",
    "education": "学历",
    "publishTime": "发布时间"
  },
  "headers": ["企业名称", "岗位", "月薪范围", "工作地点", "学历要求", "工作年限", "岗位职责", "发布日期", "福利"]
}
```

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `databaseFields` | `ImportMappingService.STANDARD_FIELDS` | 系统标准字段字典，**唯一允许的目标集合** |
| `headers` | 文件首行 | 外部表头，按列顺序逐个判断 |

### 3.2 提示词

```
你是数据导入的字段映射助手。任务是把外部表格的表头，对应到系统已定义的标准字段上。

输入是一个 JSON 对象：
- databaseFields：系统标准字段字典。key 是字段编码，value 是该字段的中文名。这是你唯一可以选用的目标集合。
- headers：外部表格的表头数组，需要逐个判断。

匹配规则，按顺序执行：
1. 先试完全匹配：表头与某个标准字段中文名完全一致，或只差空格与标点，判定「完全匹配」。
2. 再试语义匹配：含义确实等价才算匹配。例如「企业名称」可对应「公司名称」，「工作地点」可对应「工作城市」；但「期望薪资」不行，那是求职者期望，不是岗位薪资；「福利」不行，没有对应字段。
3. 语义匹配时只能从 databaseFields 已存在的 key 中选择，禁止编造不存在的字段编码，禁止输出字典里没有的中文名。
4. 匹配不到任何标准字段时，判定「待确认」，不要给候选。
5. 如果一个表头看起来是数据值而不是表头（例如「南京仙林」这种地名、「1」「2」这种序号），判定「待确认」。
6. 每个表头只能对应一个字段；同一个字段被两个表头命中时，第二个判「待确认」。

输出要求：
- 只返回一个 JSON 数组，不要解释、不要 markdown；
- 每项结构：{"mappingField":"外部表头原文","fieldKey":"标准字段编码","fieldValue":"标准字段中文名","matchType":"完全匹配|语义匹配|待确认"}
- fieldKey 必须是 databaseFields 中存在的 key；待确认时 fieldKey 与 fieldValue 填空字符串；
- 输出顺序与 headers 顺序一致，每个表头一条。
```

### 3.3 输出

```json
[
  { "mappingField": "企业名称", "fieldKey": "companyName", "fieldValue": "公司名称", "matchType": "语义匹配" },
  { "mappingField": "岗位", "fieldKey": "jobTitle", "fieldValue": "岗位", "matchType": "完全匹配" },
  { "mappingField": "月薪范围", "fieldKey": "salary", "fieldValue": "待遇", "matchType": "语义匹配" },
  { "mappingField": "福利", "fieldKey": "", "fieldValue": "", "matchType": "待确认" }
]
```

### 3.4 后端必须做的校验

| 校验 | 处理 |
| --- | --- |
| `fieldKey` 不在字典内 | 该表头降级为「待确认」，记日志（防编造） |
| 缺少某个表头的结果 | 用本地精确/别名规则补齐，保证每个表头一条 |
| 模型返回非法 JSON / 服务不可用 | 全部按本地规则回退，响应 `fallback=true` |
| 完全匹配 | `matchType=完全匹配`、`level=100%`、`status=已映射` |
| 别名/包含关系命中 | `matchType=AI 语义匹配`、`level=80%`、`status=已映射` |
| 未命中 | `matchType=待确认`、`level=-`、`status=待映射` |

### 3.5 已知限制

- 当前预览不落库、不改变导入模板；若表头与模板差异过大，预览能显示差异，但实际导入仍按固定模板解析。
- 「薪资范围」这类一列对应上下限的字段，模型只给一个字段编码，上下限拆分需后续人工确认或模板改造。

## 4. T-04 课程体系调整建议草稿

**用途：** 结合真实岗位需求与现有课程体系生成年度调整建议草稿，写入 `adjustment_plan_item`，人工采纳后生效。
**定位：** 模型只出「建议内容 + 依据」，不出项目案例编号；案例由人在案例库挑选。

### 4.1 输入

```json
{
  "recommendedTypes": ["专业方向", "课程内容", "知识技能点"],
  "notes": "基于真实岗位样本与现有课程体系生成，需院内评审",
  "jobs": [
    { "jobId": "1", "jobName": "Java开发工程师", "jd": "", "skills": ["Java", "Spring Boot", "微服务"] },
    { "jobId": "2", "jobName": "云原生运维工程师", "jd": "", "skills": ["Kubernetes", "容器化部署"] }
  ],
  "courseSystem": {
    "courseSystemId": "CURRICULUM",
    "majorName": "软件工程专业",
    "remark": "现有课程与知识技能点",
    "courses": [
      {
        "courseId": "1",
        "courseName": "软件工程",
        "outline": "",
        "positioning": "",
        "skillPoints": [
          { "spId": "11", "spName": "软件体系结构与设计模式", "goal": "", "skills": ["微服务设计", "设计模式"] },
          { "spId": "12", "spName": "云原生部署与可观测性", "goal": "", "skills": ["容器化部署", "可观测性"] }
        ]
      }
    ]
  }
}
```

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `recommendedTypes` | 调用方 | 本次要产出的建议类型，取 `专业方向`/`课程内容`/`知识技能点` |
| `notes` | 调用方 | 补充说明，有值时必须体现 |
| `jobs[].skills` | `GET /data/jobs/insights` 的 `topJobDetails.coreSkills` | 岗位真实核心技能，按 `/` 拆分 |
| `courseSystem` | `course`、`knowledge_point`、`course_knowledge_point` | 只取库中实有字段；`outline`/`positioning`/`goal` 当前为空 |

### 4.2 提示词

```
你是职业教育课程体系分析师。任务是根据产业岗位需求与本校现有课程体系，提出专业与课程调整建议的草稿。

输入是一个 JSON 对象：
- recommendedTypes：本次需要产出的建议范围，可选值为 专业方向、课程内容、知识技能点；
- notes：补充说明，有值时必须在分析中体现；
- jobs：岗位需求数据，含岗位名称与核心技能；
- courseSystem：本校现有课程体系，含专业名称、课程列表、每门课的知识技能点及其技能。

分析规则：
1. 每条建议都必须能指回输入里的具体数据。accordingTo 里写清楚是哪几个数字或对象支撑的，例如「岗位『云原生运维工程师』出现 46 次」「Kubernetes 在 44 个岗位中出现但无课程覆盖」。指不回去的建议不要输出。
2. 不要求凑数量。证据只够支撑 2 条就只给 2 条，不要为了凑数而编造理由。
3. 最多输出 6 条，按影响面从大到小排列。同一门课只出一条建议，不要拆成多条重复内容。
4. 建议必须可落地，写清楚三件事：改什么（新增、调整、合并、裁撤）、对象是谁（哪门课、哪个技能点、哪个专业方向）、怎么落地。
5. recommendedTypes 里没有的类型不要输出。
6. 不要输出项目案例编号。案例由人在案例库中挑选，你只需要在 accordingTo 里写清依据。
7. 现有课程体系已经覆盖的内容，不要作为新增建议提出；判断覆盖关系时，以技能点关联技能与岗位技能比对为准。
8. 不得提出「新设专业」「撤销学院」这类超出专业方向调整范围的动议。

优先级判定：
- 高：技能在岗位中高频出现，且现有课程完全没有对应技能点；
- 中：现有课程有部分覆盖，但技能点内容滞后或深度不足；
- 低：加分技能、小众岗位需求，可选增补。

输出要求：
- 只返回一个 JSON 对象，不要解释、不要 markdown；
- 结构：{"items":[{"recommendedType":"课程内容","level":"高优先级","title":"建议简短标题","desc":"详细建议，写清做什么、怎么落地","accordingTo":["依据1","依据2"]}]}
- recommendedType 只能是 专业方向、课程内容、知识技能点 三个值之一；
- level 只能是 高优先级、中优先级、低优先级 三个值之一；
- accordingTo 至少一条，每条必须含具体数字或具体对象名称；
- 每个输入类型至少输出一条（数据确实不足时除外）。
```

### 4.4 后端必须做的校验

| 校验 | 处理 |
| --- | --- |
| `recommendedType` 不在 `recommendedTypes` 内 | 丢弃该条 |
| `recommendedType` 无法映射到 DIRECTION/COURSE/SKILL | 丢弃该条 |
| `accordingTo` 为空 | 丢弃该条（建议须可回溯到数据） |
| 未覆盖三类 | 整批回退现有规则生成 |
| 条数超过 6 | 按优先级截断保留前 6 条 |
| 已采纳建议 | 重新生成时保留原内容与 `ADOPTED` 状态，不覆盖 |
| 模型不可用 / 非法 JSON | 回退规则生成，响应中标注来源 |

**落库口径：** `suggestion_no` 按 `ADJ-{planYear}-{D|C|S}{三位序号}` 生成；`priority` 映射为 `HIGH/MEDIUM/LOW`；`basis` 由建议描述与依据拼接；`status` 初始为 `PENDING`。

### 4.5 已知限制

- 课程表无 `outline`、`positioning`、`goal` 字段，模型无法判断课程内容陈旧度，只能判断技能覆盖缺口。
- 岗位技能来自看板 `topJobDetails.coreSkills`（每岗最多 3 个），不是全量 JD；建议粒度相应受限。

## 5. 未纳入的模板与原因

| 源模板 | 是否纳入 | 原因 |
| --- | --- | --- |
| 标准标签映射建议 | 否 | 本项目没有「外部标签→课程标签」的人工确认流程，`skill_tag` 只有 `tag_name/tag_type`，强行映射会污染技能热度统计 |
| AI 协同岗位判定 | 否 | 看板 AI 岗位占比当前按岗位名称关键词统计（`StatsMapper.countAiJobs`），不调用模型；改为模型判定需先变更 `spec.md` 与统计口径，避免指标前后不可比 |
| 软数智云企业判定 | 是（T-02） | 仅保留 `aiFlag` 0/1，未引入赛道分类字段；当前结果不落库 |
| 报告正文生成 | 否 | 报告由服务端模板渲染，模型不参与长文生成 |
